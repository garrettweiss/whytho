# WhyTho launch security audit and remediation

> **October 31 release update:** The approved database and application release is now live at whytho.us. See [production release and acceptance evidence](PRODUCTION_RELEASE.md) for the current status, final migration versions, 50 account database scenarios, and remaining launch gates. The assessment below records the pre-release work; references to undeployed/local-only fixes describe that earlier checkpoint.

Assessment: October 30, 2026, America/Los_Angeles. Scope: current application source, dependency lockfile, read-only production Supabase catalog/advisors, synthetic local PostgreSQL tests and isolated route/component tests. No production database changes, deployments, destructive scans, real-user impersonation or third-party messages were performed.

The release candidate fixes the identified privilege-escalation, verification, account-race, private-data and paid-endpoint exposure issues. **The live site is not yet protected by the unapplied migrations and undeployed code.** Broad promotion must wait for the deployment and provider acceptance gates below. This is a source/configuration review and targeted adversarial test exercise, not an exhaustive penetration-test certification.

## Prioritized findings and fixes

| Priority | Finding and demonstrated consequence | Implemented correction | Evidence / deployment condition |
|---|---|---|---|
| P0 | A signed-in user could update their own `user_profiles.is_admin`, and five Jack RLS policies trusted that editable field. An owner-only row policy did not protect privileged columns. | Revoke browser profile writes, including column grants. Jack authorization uses server-managed JWT `app_metadata.is_admin`. Existing field values no longer grant authority. | Read-only live catalog; actual local self-promotion denial and trusted-claim positive test. Requires security migration. |
| P0 | Claimant-controlled websites and unrelated `.gov` accounts could serve as identity evidence. Resuming an old challenge could retain obsolete source authority. | Private operator-reviewed source anchors; exact website/domain and evidence binding in API and completion trigger; current admin membership rechecked under locks; two distinct completed methods for the same actor. Stale pending/completed proofs cannot be resumed after source changes. | API source-change regressions and real SQL negative/positive tests. New automatic verifications fail closed until reviewed source rows exist. |
| P0 | Team membership changes could target another profile; separate permission checks and writes admitted claim, last-admin and publication races. | Account operations use narrow service-only transactional RPCs, profile-first lock order, same-profile target checks, last-admin protection and question-serialized publication. | 46 PostgreSQL assertions/scenarios, including four concurrent transaction scenarios. See account report. |
| P1 | Original account RPC integration assumed the service role could read `auth.users`; live catalog proves it cannot. The local fixture's excess grant hid the failure. | Three account functions are SECURITY DEFINER, explicitly owned by `postgres`, with `pg_catalog` search path and qualified application objects. PUBLIC/anon/authenticated execution is revoked. Authenticated actor IDs come only from the API's verified session. | Corrected fixture grants no auth-table read access and proves successful service calls plus direct browser rejection. Independent reviewer confirmed the privilege boundary. |
| P1 | Chat clients could provide privileged message roles, excessive input, and trigger private/service-role reads or direct question publication through model tools. | Only bounded user/assistant text accepted; 128 KiB streamed JSON limit, 40 messages, 4,000 characters/message and 24,000 total characters. Public read client for civic tools, draft filtering, question preparation only, four model steps and 1,500 output tokens. | Helper tests, code inspection, real SDK/provider mocked-stream compatibility test. Model outputs remain untrusted; no tool can grant account authority. |
| P1 | In-memory quotas reset across server instances; OTP generation/attempts and paid model traffic needed shared limits. | Atomic database counters for chat, anonymous signup, claims, email/meta verification and photo upload. Failure of the quota store blocks the protected action. Question quotas use a per-user transaction lock. Cryptographic OTPs, expiry, bounded guesses and secret clearing on success. | Parallel counter test admits exactly 3 of 10 calls; question test admits exactly 3 of 8 concurrent submissions to one profile. OTP expiry/attempt/provider tests. |
| P1 | Arbitrary verification URLs and image processing could expose server-side fetching or unsafe uploads. | Reviewed HTTPS sources; public IPv4 DNS checks and connection pinning; no redirects; 50 KB HTML limit and one eight-second deadline spanning DNS, connection setup and body. Pinned read-only HTTPS transport checked against a public official site; its 403 response was not treated as verification success. |
| P1 | Runtime dependencies included publicly disclosed vulnerabilities. | Updated Next, Sentry, AI SDK/provider, Zod and sharp; patched applicable transitive packages; moved CLI-only shadcn to development. Chat stream client migrated and compatibility tested. | Runtime audit: 30 findings before (4 critical, 13 high, 12 moderate, 1 low), 0 after. Entire tree still has 20 development-tool findings (17 moderate, 3 low), no high/critical. Audit files retained. |
| P1 | Civic/profile identity and user text could reach session replay, error payloads and analytics. | Replay and tracing rates zero; Sentry allowlist keeps technical exception metadata while dropping identity, requests, arbitrary messages, context, breadcrumbs, tags and attachments. Browser product analytics disabled in the integrated privacy work. | Error telemetry fixture includes identity and civic fields and confirms removal. Production vendor settings and historical retention remain operator/legal tasks. |
| P2 | Cross-origin browser mutations, unrestricted embedding, mutable function search paths and unnecessary SQL privileges enlarged the attack surface. | Same-origin/Fetch Metadata checks, restricted mutation content types, security headers, fixed legacy function search paths, browser trigger-RPC and maintenance privilege revocations, no browser CREATE in public schema. | Request-policy tests and real SQL privilege checks; deployed headers still need smoke verification. |
| P2 | Broad claims about chatbot global rankings or counts could misrepresent sampled/permission-filtered data. | Removed unsupported sampled rankings and anonymous vote-count claims; distinguish human official answers from AI analysis; direct users to canonical views. | Code review and integrated AI evidence tests. Production read-only review found RLS enabled on every public table. It found one profile admin flag, two server-managed admin claims and no flagged account lacking the server-managed claim; this observation is not proof that the exploitable policy was never abused. Inspect administrative activity during rollout and retain evidence before any remedial data changes.

## Executed verification

- `npm run type-check`: passed with the final patched dependency tree.
- `npm test`: **137/137 passed in final integration** (134 at the security checkpoint, plus three fetch-deadline regressions), covering public directory/profile logic, account handlers/pages, portrait handlers and byte validation, AI evidence, notification planning and security behavior. External auth/email/model boundaries are mocked where indicated in each test; no messages or paid model calls were made. See [final integrated tests](evidence/final-tests.log).
- Account PostgreSQL suite: **42 assertions plus 4 real concurrent scenarios passed**, against synthetic users with production-like service-role auth-table privileges. Repeat application preserves audit history.
- Combined security PostgreSQL suite: **25 SQL assertions plus counter/question concurrency checks passed**. It applies the release, account, security and portrait migrations in order and repeats the security migration. All fixture public tables keep RLS. No live fixture was created.
- Final source secret-pattern scan: **327 tracked/nonignored source files, zero matches**. It excludes ignored environment files and Git history; it does not establish that no secret was ever committed.
- Independent security reviewer tested stale reviewed-source changes and reviewed the final account definer permissions. The security specialist reviewed the portrait routes/RPCs independently of their implementation.
- Three additional real-fetcher regression tests passed with synthetic DNS/HTTPS/clock boundaries: DNS delay consumes the total budget, continuous body trickling is aborted at eight seconds, and completed HTML/redirect rejection clear the timer. The late OS DNS lookup result is ignored because the platform resolver cannot be cancelled. [Deadline test evidence](evidence/verification-deadline-tests.log).
- Targeted security ESLint and `git diff --check` passed. Full build and final lint status are recorded in the consolidated launch evidence after integration. The first integrated lint pass found generated-file/test-loader and pre-existing script warnings; this report does not label that initial pass clean.

Portrait upload authorization is checked before storage and again at publication. If authority is revoked between those steps, the profile update fails. The uniquely named uploaded object can remain in the public portrait bucket; the API does not claim transactional rollback of external storage. Any later cleanup requires the owner's explicit data-deletion approval. The upload workflow therefore accepts public portrait material only, never sensitive identity evidence.

## Deployment order and recovery

1. Confirm `20261031041730_release_rls_hardening.sql` is already applied; otherwise include it in the reviewed rollout. Capture backups/policies and verify all public tables have RLS.
2. Apply `20261031205615_account_transitions.sql`, then `20261031205619_launch_security.sql`, then `20261031205623_portrait_permissions.sql`. Each migration is transactional; the security migration aborts if a public table lacks RLS. The source table is intentionally empty.
3. Deploy the matching package lockfile and application. New rate-limited routes intentionally return 503 if their database function is absent. Do not deploy those routes ahead of the schema.
4. Import reviewed authority rows, then run controlled provider acceptance and deployed-header checks. Keep public promotion gated until account ownership and privacy controls pass.
5. If the application release fails, keep the privilege corrections and private schemas in place. Disable affected features or restore compatible application code while preserving access controls. Do not restore editable admin flags, permissive verification policies or browser RPC execution to make an old route work. This plan performs no rollback deletion.

Reproduce with `npm test`, `npm run type-check`, `npm run lint`, `sh scripts/test-account-database.sh` and `bash scripts/test-launch-security.sh`. Database scripts use new socket-only local PostgreSQL 17 clusters, retain the synthetic evidence and stop the local server afterward. They do not read production database URLs.
