# Politician identity technical audit and repair design

Date: 22 November 2026  
Owner: WT, supporting Esteban's directory-wide read-only audit  
Status: planning only. No application code, migrations, production rows, files other than this document, or external messages were changed by this audit.

## Recommendation

Represent one real person with one canonical public profile, retain every existing politician ID and slug as a source identity, and preserve the original question, answer, vote, verification, media and audit records. Select the best supported value **per field**, rather than selecting one row and discarding everything else.

The repair needs both a reviewed duplicate manifest and a shared identity resolver for every importer. Correcting state spelling alone will not prevent the other failure modes below. Names, photos, shared office, and matching political party are discovery clues, not sufficient merge authority.

The safe first production cohort consists of high-confidence duplicate groups with no unresolved identity or authority conflicts. AOC is a strong example, but no group is authorized for mutation by this document.

### Uniqueness and security facts to carry into the design

- The baseline has unique `politicians.slug`, unique `fec_candidate_id`, and a separate partial unique index on `candidate_fec_id`. There is **no cross-column FEC uniqueness**. A value can identify separate rows through different columns. There is no declared unique `fec_id`, `bioguide_id` or `openstates_id` in the checked-in migration set; verify live catalog.
- Copying a losing row's `candidate_fec_id` onto a canonical row while keeping the losing row violates that column's unique index. Keep raw source IDs where they are and register them against the canonical identity in a separate table; do not null historical source identifiers just to satisfy an update.
- Blanket ID replacement collides on team members, alias names, race membership, weekly snapshots, notification preferences and potentially future identity constraints. `ON CONFLICT DO NOTHING` would silently discard meaning, not resolve the conflict.
- Public read policies on source politicians and aliases are broad; private tables and drafts have narrower policies/grants. A new canonical view/RPC must not use service access to leak drafts, verification codes, team emails, source-review notes or private merge evidence.
- Use RLS and explicit grants/revokes for every new table and function. A merge execution RPC is service/admin only with fixed `search_path`, bound authenticated actor, reviewed manifest and no client-supplied authority.
- Existing answer, media, claim, team, verification, portrait and notification functions take locks in differing orders. A new merge operation must use a documented compatible order and exercise races; do not hold an identity lock then call old RPCs in an opposite order without analysis.
- Preserve audit append-only grants; do not temporarily grant service UPDATE/DELETE to historical ledgers as a shortcut.
- No politician favorites/follows/subscriptions table or vector/embedding column/index was found in checked-in schema/code or the exposed live metadata. This is a scoped negative finding, not proof no private/remote feature exists. Confirm `pg_catalog`, external search stores and runtime jobs before rollout.

## Identity and preservation model

### Canonical identity registry

Proposed additive model, subject to schema design review:

1. **Canonical identity:** choose one existing `politicians.id` and its permanent slug as the public canonical profile. Do not generate a new UUID or prettier slug merely to clean up duplicates.
2. **Approved profile membership:** source profile UUID -> canonical UUID, identity decision version, approved manifest/run, evidence and effective time. One active root per source; reject cycles, chains, test/real mixing and mapping to an unresolved target. Private decision evidence belongs in a separate protected ledger. The public projection needs only approved IDs/slugs.
3. **External identifiers:** one person can have many `(namespace, external_id)` identifiers. Namespaces distinguish Congress/Bioguide, OpenStates person, FEC candidate, VoteSmart and GovTrack. FEC candidate IDs across offices/cycles map to one person when proven; election cycles belong to candidacy observations, not the uniqueness key for the same provider ID. Provider identifiers must not be confused with committee/office/term identifiers. Preserve raw ID columns and observations.
4. **Dated source observations:** source record, retrieved-at, effective date/cycle, raw normalized fields, provider ID, source URL and review status. Conflicting observations remain available; a later null is not a deletion instruction.
5. **Office tenures and candidacies:** separate associations keyed by person, normalized jurisdiction/office/seat, election/term and source. `is_candidate`, party, district and outcome are time-dependent facts. Losing a race cannot deactivate a person's existing record, and running for a new office cannot overwrite the office held.
6. **Field selection provenance:** record selected value, source/profile ID, evidence/reviewer/date, previous value and selection rule. Preserve manual lock/review status so later imports cannot undo a decision.
7. **Merge decision and rollback ledger:** immutable manifest, reason, competing identities, selected canonical ID, per-field choices, dependencies/hash/version, actor, approvals and before-state. Application of the mapping is idempotent. A later reversal is a new decision, not deletion of the original evidence.

Use a normalized state code for matching and a display-name mapping for presentation. Normalize district `014`/`14`, at-large forms, office taxonomy, Unicode/spacing and known name variants for *candidate discovery*. Retain the original name and state strings. State, district and office changes over time must not split a known provider identity.

### Match confidence

| Class | Evidence | Action |
|---|---|---|
| Proven provider identity | Same correctly typed stable external ID, or reviewed authoritative crosswalk; no conflicting strong ID | Eligible for approved canonical mapping, subject to authority/history guards. A shared bad imported ID still requires investigation when other evidence conflicts. |
| Strong candidate duplicate | Exact normalized full name, normalized state, same chamber/seat and temporal compatibility; one Congress official and incumbent FEC entry; no conflicting IDs | Review against primary source/crosswalk before applying. AOC fits this mechanism. Do not auto-merge the whole class just from name/state. |
| Possible identity across roles | Aliases, middle initials, renamed person, state/office change, several FEC IDs, shared biography/official URL | Review separately; source-backed person continuity required. |
| Ambiguous or conflicting | Different Bioguide/OpenStates IDs, homonyms, parent/child suffixes, competing claims, inconsistent dates/seat, incompatible source identities | Hold. Do not choose a winner by completeness or popularity. |
| Same office, different person | Successor/predecessor, challenger/incumbent, shared institutional URL/portrait host | Keep separate people. Model office/seat relationship explicitly. |

The audit must search **within all states/offices and across them**, not only same-name/same-state pairs, because the same person can run for another office or change name. Candidate generation can be broad; approval cannot be broad. Persist "reviewed distinct people" decisions so repeated imports do not reopen the same false match.

**Do not automatically merge transitive candidate groups.** If A resembles B and B resembles C, that does not establish that A and C are the same person. Validate all accepted group members together against strong identifiers and conflicting evidence; record rejected edges. ## Execution design and rollout gates

1. **Catalog and writer freeze plan.** Before implementation approval, capture live schema version, migrations, all FKs, indexes, unique/exclusion constraints, triggers/function definitions, policy/grant fingerprints, storage path contracts, cron/realtime publications and remote import jobs. The audited migration set must match live. Do not pause jobs yet under a planning-only instruction.
2. **Manifest with individual decisions.** Record each approved group's members, canonical ID/slug, evidence, confidence, field choices, preserved conflicts, per-table dependent counts and source-row hashes. Separate unresolved/homonym/claimed groups. Include exact "no deletion, no authority widening, no external messages" invariants.
3. **Prevention first.** Implement shared normalization and one transactional resolver. All writers call it; no failed lookup falls through to insertion. Acquire deterministic locks around stable source identity keys, re-read after locks, enforce unique namespace/ID ownership and retry uniqueness conflicts by resolving, not appending a new slug. Unmatched ambiguous imports enter private review staging. Protect canonical slug, tier, team, reviewed edits and portrait provenance from importer allowlists.
4. **Additive schema and compatibility release.** Create registry, membership, observations and decision ledger with RLS/grants. Populate identity mappings in an inactive/draft state. Readers and mutation authorization must support mappings before activation. Test with both current live schema and the local notification/correction migrations in place.
5. **Offline rehearsal and reviewed dry-run.** Use synthetic and sanitized data, including live anomaly shapes and non-empty historical tables. Produce a per-group before/after report and invariant results. No service-role API, real user auth or provider message should run in tests.
6. **Apply-time recheck.** Regenerate group evidence immediately before action. Lock source profiles in deterministic UUID order, check unchanged identity/authority fields, dependency counts/version and newly written content. Stop on any new claim, verification, external-ID conflict or unreviewed human edit. Re-run the cheap discriminating checks for the cohort, not only the original name match.
7. **Back up and activate small cohorts transactionally.** Keep RLS-locked, idempotent before-state/manifest copies; protect all secrets/private data. Apply approved mappings and selected field overlays, retain original rows and immutable ledgers. Commit canonical identity ownership and mapping atomically; no interval where old writer can recreate the duplicate. Start with AOC and a small representative unclaimed cohort, then bounded batches.
8. **Invalidate and verify each cohort.** Confirm old URLs/anchors work, public lists show one person, all source record IDs remain reachable through canonical profile, numeric totals match, no drafts leak, team permissions are unchanged and no notification was queued/sent. Confirm idempotent rerun is a no-op and importer replay does not produce a new person.
9. **Rollback through a new decision.** Preserve original rows and ledgers. Deactivate/reverse mapping and field overlay using manifest plus optimistic version guards; never overwrite legitimate post-merge edits with stale backup. New post-merge questions/claims may require manual split decisions, so rollback is not a blind reverse UPDATE. Do not delete registry/audit/backup rows.
10. **Only then broaden.** Monitor new unresolved identities and alias hits, importer conflicts, duplicate creation attempts, missing profile content, source-field changes, query latency and cache behavior. Resolve ambiguous groups by reviewed evidence, not by relaxing the matching rule.

Production application requires a concrete approved manifest and migration/deployment authorization. The current user request authorizes this audit and plan only.
